### 4.3 Notebook 中 Markdown 的书写规范（表格不渲染的头号原因）

Markdown 把标题、段落、表格、列表、代码块、引用、分隔线各自视为**独立块**。
**规则：任意两个不同的块之间，必须至少有一个空行**；否则解析器会把它们合并成一段普通文字，
表格语法（`| ... |`）就会原样显示为竖线文字，而不是表格。

#### 4.3.1 强制写法（照抄这个模板）

```
## 一级标题

### 二级子标题

正文段落写在这里。段落结束。

| 列1 | 列2 | 列3 |
| --- | --- | --- |
| 内容 | 内容 | 内容 |

后续正文另起一段。
```

#### 4.3.2 六条硬规则

1. **标题后必须空行**。`## 标题` 下一行若直接是正文或表格，标题和正文会被并成一段。
2. **表格前必须空行**。表格 `|` 行的上一行必须是空行；紧跟在正文文字后面时，表格不渲染。
3. **表格后必须空行**。表格最后一行的下一行若是正文，表格块会被截断（Jupyter 下常整体失效）。
4. **表格必须独立成行**。表头、分隔行 `| --- | --- |`、每个数据行各占一行，不能与前后文字挤在同一行。
5. **分隔行 `---` 不能省**，且每一列都要有 `---`；列数（竖线数）必须全表一致。
6. **竖线必须是英文半角 `|`**。中文全角 `｜` 不识别为表格。

#### 4.3.3 两个特殊坑

- **`---` 分隔线不要紧贴标题**。`---` 紧跟下一行的文字时，可能被解析为"给上一行加下划线"而改变块类型。
  安全写法是给 `---` 前后都留空行。
- **单个 Markdown 单元格内不要混排过多块类型**。若一个单元里同时有标题、正文、表格、代码块，
  务必逐块检查空行；把内容拆到多个单元是更稳的做法。

#### 4.3.4 更底层的一类故障：source 数组的换行

上面 4.3.1~4.3.3 讲的是"文本内部的空行"。还有一类故障发生在**更底层**——单元格文本本身就对，
但存进 `.ipynb` 的 `source` 数组时换行丢了或被翻倍，导致**整段文字在 Jupyter 里被粘成一行**，
表现为标题和表格全部变形（例如渲染成 `## 2 算法实现### 2.1 ...| 指标 | 定义 || --- | --- ||`）。

`.ipynb` 中单元格正文以 `source` 数组存储，Jupyter 渲染 markdown 时按 **`"".join(source)`** 拼接。
因此数组元素**必须自带行尾换行符**，规范形式为：

```json
"source": ["## 2 算法实现\n", "\n", "### 2.1 流程\n", "\n", "| 列1 | 列2 |\n", "| --- | --- |\n"]
```

**两种错法都会致命：**

| 错法 | 后果 |
| --- | --- |
| 元素为裸行、不含 `\n`（`['a','b','c']`） | `"".join` 得 `'abc'`，**所有行粘成一行**，标题与表格语法全部失效 |
| 元素自带 `\n`，却再用 `"\n".join` 还原 | 每个换行翻倍成空行，**代码块与表格被空行撑破**，表格不渲染 |

**结论：还原文本时按格式自适应，写回时统一成规范形式。** 本工程的实现见：

- `DIP\0202\build_nb.py` 的 `_to_source()`：用 `splitlines(keepends=True)` 生成自带换行的数组；
- `DIP\_tools\exec_nb.py` 的 `cell_text()`：先判断元素是否自带换行，再决定用 `""` 还是 `"\n"` 拼接；
  写回时统一 `splitlines(keepends=True)`。

**因此：不要手写或手工拼接 `source` 数组。** 一律通过 `build_nb.py` 生成、用 `exec_nb.py` 执行回写。

#### 4.3.6 其他必查项

- 表格必须写在 **Markdown** 单元格里；Code 单元格只会原样输出文本，不做渲染。
- 不要从 Word/网页直接粘贴，会带入零宽字符、全角空格等隐形字符，破坏解析。
- 代码块用三个反引号独立成行，且上下都要空行。

### 4.4 Word 版论文的公式：渲染为图片插入（默认方案）

**python-docx 不支持数学公式。** 若只把 LaTeX 里的反斜杠删掉、当普通文字写进去，结果会是
`R(x,y)=frac{sum_{u,v}[T(u,v)-bar{T}]...}` 这种残骸——公式完全不可读。

**结论先行：本工程默认把公式渲染成 PNG 图片插入。** 原因见第 9 节坑 8——Word 原生公式
（OMML）方案在本机 Office16 上会因某些嵌套结构被拒开，排查多轮仍未通过，故改用图片方案。

| 项目 | 做法 |
| --- | --- |
| 渲染器 | `DIP\_tools\mathimg.py`，用 matplotlib 的 mathtext（自带，无需 LaTeX 发行版） |
| 显示公式 | 居中图片，高度按宽高比自适应（上限 3.0 cm），编号接在后面 |
| 行内公式 | 图片作内联对象插入，高度 ≈ 1.55 倍字号 |
| 分段函数 | mathtext 不支持多行 `array`，**手工绘制**：各行分别渲染 + 花括号拉伸拼合 |
| 中文变量 | `\mathrm{像素为前景}` 需配置 CJK 字体，否则渲染成方块 |
| 缓存 | 按公式内容哈希存入 `_tools\_eqcache`，同一公式只渲染一次 |
| 兜底 | 渲染失败退回纯文本，绝不中断整篇文档生成 |

代价：**公式不可在 Word 中编辑**。若日后 OMML 问题解决，可切换：
`set DOCX_MATH=omml`，此时改用 `_tools\omml.py`（LaTeX → OMML 转换器）。

**验收方式（必做）**

```powershell
python D:\workspace\Jupyter_WorkSpace\DIP\_tools\verify.py 0202
```

第 6 类检查会核验：公式是否已渲染为图片插入、图片是否写入包内，
并**调用 Word COM 真实打开一次文档**——这是判断文档能否使用的最终判据。

> **三个配套注意点**
>
> 1. 判断 Office 文档能否打开，唯一可信的判据是**用 Office 自己打开一次**。
>    zip 完整性、XML 可解析、python-docx 可读、甚至 Schema 校验通过，**都不等于** Word 能打开。
> 2. 提取 Word 文本做核对时要注意公式的呈现形式：图片方案下公式内容根本不在文本层，
>    因此**不得**把公式里的数字当作"应出现在 Word 文本中的指标"去核对
>    （校验器已剔除公式内容）。若切回 OMML，则须遍历 `m:t` 节点。

## 9 已踩过的坑（故障速查表）

以下问题都在本课程设计中**真实发生过**，每一条都注明症状、根因、以及下次如何避免。
开工前扫一遍，可省下大量返工时间。

### 9.1 Notebook 渲染类

#### 坑 1　整个 Markdown 单元格被粘成一行，标题与表格全变形

**症状**：Jupyter 里看到
`## 2 算法实现### 2.1 完整流程输入：视频序列...| 指标 | 定义 || --- | --- ||`
标题、代码块、表格挤成一行，表格不渲染。

**根因**：`.ipynb` 的 `source` 数组元素**不含行尾换行符**，而 Jupyter 渲染 markdown 时按
`"".join(source)` 拼接。元素若是裸行（`['a','b','c']`），拼接结果就是 `'abc'`。

**避免**：
- 生成 notebook 时用 `splitlines(keepends=True)`，让每个元素自带 `\n`；
- **不要手写或拼接 `source` 数组**，一律由 `build_nb.py` 生成、`exec_nb.py` 回写；
- `check_md.py` 会检查"source 元素是否自带行尾换行"。

#### 坑 2　换行被翻倍，代码块与表格被空行撑破

**症状**：表格依然不渲染，但这次文档里到处是多出来的空行。

**根因**：元素**已经自带** `\n` 了，还原文本时又用 `"\n".join()`，每个换行变成两个。
这是修复坑 1 之后引入的**连锁错误**（改了写入端，忘了读取端）。

**避免**：还原文本必须**格式自适应**——先判断元素是否自带换行，再决定用 `""` 还是 `"\n"` 拼接。
`exec_nb.py` 的 `cell_text()` 已按此实现。`check_md.py` 会检查"连续空行是否过多"。

#### 坑 3　用错误的方式"读"文件去诊断，导致误判

**症状**：我连续两轮判断"换行正常"，实际是坏的；随后又误判成"表格缺空行"。

**根因**：诊断脚本用了 `"".join(source)` 去还原文本——**复现了渲染器的错误拼接方式**，
等于拿有 bug 的尺子去量坏掉的东西。

**避免**：排版问题**必须用渲染结果验收**，不要靠肉眼或自写脚本读源码：

```powershell
python -m nbconvert --to html --stdout "xxx.ipynb" | findstr /C:"<table"
```

表格数应 ≥ 实际表格数；若为 0 则渲染失败。

### 9.2 Word 生成类

#### 坑 4　公式变成一串残骸（`frac{sum_{...}}`）

**症状**：Word 里公式显示为 `R(x,y)=frac{sum_{u,v}[T(u,v)-bar{T}]...}`，
或下标丢失成了普通文字（`σk²` 而非 `σ_k²`）。

**根因**：**python-docx 不支持数学公式**。当时只把 LaTeX 的反斜杠删掉当普通文字写入，
`\frac` 的 `\` 一删就剩 `frac`。

**避免**：公式必须转换为 **OMML（Office Math Markup Language）** 再插入。
现成转换器见 `_tools\omml.py`，由 `build_docx_md.py` 调用。转换后必须检查
**无残留 `\` 开头的 LaTeX 命令**。

#### 坑 5　公式文字不在 `paragraph.text` 里，导致校验误报

**症状**：校验器报"数值 `2.5` 在 docx 中缺失"，但 Word 里明明有。

**根因**：公式渲染为 OMML 对象，其文字在 `m:t` 节点中，**不在** `paragraph.text` 里。

**避免**：任何"提取 Word 文本做核对"的脚本，都必须同时遍历 OMML 的 `m:t` 节点
（`verify.py` 已实现）。

#### 坑 6　Word 锁文件导致无法覆盖写入

**症状**：重新生成 Word 时报错或文件未更新。

**根因**：Word 打开文档时会生成 `~$xxx.docx` 锁文件，同名文件被占用。
另外 `glob("*.docx")` 会把锁文件也匹配进来，读它会报 `BadZipFile`。

**避免**：**生成前先关闭 Word**；脚本里过滤掉以 `~$` 开头的文件。

#### 坑 7　校验器的统计口径与生成器不一致

**症状**：校验报"md 表格 6 个 / docx 5 个不一致"，但实际内容完全正确。

**根因**：校验器按"表题（`**表N　**`）"计数，生成器按"实际表格块"计数，
伪代码表被算重了。同类问题还有"参考文献从第一次出现'参考文献'处开始数"——正文里
提到"参考文献"就会数错。

**避免**：**校验口径必须与生成口径一致**。统计表格要用"表头行 + 分隔行"的判定方式；
统计文献要从**最后一次**出现"参考文献"处切分。

#### 坑 8　【致命】Word 拒绝打开含 OMML 公式的文档

**症状**：Word 弹出「文件可能已经损坏」，文档打不开；但 zip 完整性正常，
lxml、python-docx 都能正常读取，Schema 校验也通过——**"XML 能解析"却打不开**。

**排查过程（结论来之不易，按这个顺序查最快）**

1. 用 **Word 自身**判定，别靠猜测。开 COM 直接打开一次，捕获真实报错：

   ```python
   import win32com.client as win32
   word = win32.Dispatch("Word.Application")
   word.DisplayAlerts = 0
   word.Documents.Open(str(path), ReadOnly=True)   # 报错即为 Word 的真实判定
   ```

   实测结果：含 OMML 的文档报 `文件可能已经损坏 (wdmain11.chm, 25272)`，
   不含 OMML 的同款文档正常打开。

2. **逐个公式单独建文档二分**，定位到具体公式。实测最终锁定为
   **"分式内部嵌套上下标"**（如 `\frac{D^{2}}{2D_0^{2}}`、`\frac{a^2}{b}`）。
   注意：`\frac{a}{b}` 单独可用、`D^{2}` 单独可用，**组合起来就失败**。

3. **命名空间声明被误删**也是一个独立诱因：曾用
   `lxml.etree.cleanup_namespaces()` 清理"冗余"的 `xmlns:m`，结果把根元素
   `<w:document>` 上由 `mc:Ignorable` 引用的扩展命名空间（`o`、`r`、`v`、`wp`、
   `w10`、`w14`、`wp14`…）一并删除，根元素声明数由 **17 个锐减到 3 个**，
   Word 立即报损坏。**绝对不要对 docx 调用 `cleanup_namespaces`。**

4. 修掉上述两点后，本机 Office16 仍会拒绝"分式内嵌套上下标"的 OMML。
   这是 Word 侧未公开的额外约束，**不再继续深挖**。

**最终采用的方案：公式渲染为图片插入（默认方案）**

```powershell
python D:\workspace\Jupyter_WorkSpace\DIP\_tools\build_docx_md.py 0303
```

`_tools\mathimg.py` 把 LaTeX 用 matplotlib 的 mathtext 渲染成 PNG（自带，无需
LaTeX 发行版），再由 `build_docx_md.py` 以图片形式插入。优点：

- **保证 Word 一定能打开**（已由 Word COM 实测验证）；
- 分式、根号、上下标、求和、分段函数显示效果与 LaTeX 一致；
- 转 PDF、打印、送审均无问题。

代价：**公式不可在 Word 中编辑**（OMML 可以）。若日后 OMML 问题解决，
可用环境变量切回：`set DOCX_MATH=omml`。

**已验证的实现要点**

| 项目 | 做法 |
| --- | --- |
| 显示公式 | 居中图片，高度按宽高比自适应，上限 3.0 cm；编号接在后面 |
| 行内公式 | 图片作为内联对象插入，高度 ≈ 1.55 倍字号 |
| 分段函数 | mathtext 不支持多行 `array`，改为**手工绘制**：各行分别渲染 + 花括号拉伸拼合 |
| 中文变量 | `\mathrm{像素为前景}` 需配置 CJK 字体，否则渲染成方块 |
| 渲染缓存 | 按公式内容哈希命名存入 `_tools\_eqcache`，同一公式只渲染一次 |
| 失败兜底 | 渲染失败退回纯文本，绝不中断整篇文档生成 |

**验收方式（必做）**

```powershell
python D:\workspace\Jupyter_WorkSpace\DIP\_tools\verify.py 0202
```

`verify.py` 已加入一项**真实的 Word 打开检查**（调用 COM 打开一次），
这是判断"文档是否可用"的最终判据——lxml 能解析、python-docx 能读、
Schema 校验通过，都**不等于** Word 能打开。

> **本坑的核心教训**：判断 Office 文档是否可用，唯一可信的判据是
> **用 Office 自己打开一次**。中间层（zip 完整性、XML 可解析、python-docx 可读、
> 甚至 Schema 校验）全部通过，Word 依然可能拒绝打开。
> 另外：OOXML 有 Schema，元素标签（`m:sub`/`m:sup` 不能写成 `m:e`）、顺序、
> 必填项都要合规；且不要用 `cleanup_namespaces` 动 docx 的命名空间。

### 9.3 工程环境类

#### 坑 9　PowerShell 内联 Python 的引号被吞

**症状**：`python -c "..."` 里的引号、反斜杠被 PowerShell 解析掉，报语法错误。

**避免**：**不要在 PowerShell 里内联多行 Python**。把脚本写成 `.py` 文件再执行；
必须内联时，输出也不要拼 `|` 字符（会被当成管道符）。

#### 坑 10　`_scratch` 目录不存在导致写日志失败

**症状**：`FileNotFoundError: ...\_scratch\run_report.txt`。

**避免**：写日志前 `LOG.parent.mkdir(parents=True, exist_ok=True)`。
每个章节目录首次运行前先建 `_scratch\`。

#### 坑 11　在 `python -c` 里写 f-string 含反斜杠

**症状**：`SyntaxError: f-string expression part cannot include a backslash`（Python 3.11）。

**避免**：把正则或含反斜杠的表达式提到 f-string 外面，或改用脚本文件。
